For each email the two replies were shown side by side. Which model sat on the left was random per email, and the model names stayed hidden until the scoring was done. The quote table is inserted by code and is the same on both sides, so it was replaced with a placeholder; the one exception is T05, where the models detected different languages and got a Chinese and an English table.

## 3. Things the replies said that the system never did

Found while comparing the replies with the routing rules. Neither `Assemble & Check` nor `Grade` looks for these; both only check amounts, discounts, refunds and free shipping.

| Email | Model | What the reply said | What the system actually does |
|---|---|---|---|
| T29 | Haiku | "Your case has been flagged for priority review." | Customs emails go to `human_review`; nothing marks them as priority. |
| T05 | Sonnet | 「運費請參考報價內容。」 | The quote table has no shipping line. |
| T05 | Haiku | "including the shipping estimate to Los Angeles that you asked about" | Same. |
| T19 | Sonnet | "questions about duties, taxes, customs or import documents will be answered separately" | The customer asked nothing about customs. |
| T02 | Sonnet | Repeated the customer's item list before the quote table. | Not wrong, but the table already lists the items. |

In the blind review I picked the Haiku reply for T29, the one with the made-up promise. The problem only came up when Claude checked the replies against the routing rules. The sentence sits inside an otherwise normal reply, so the person reading the draft can miss it too.

Not fixed yet. Plan: a `Draft Reply` prompt rule (do not mention anything the quote table does not contain; answer shipping questions with "a colleague will reply"; outside `escalate`, never say the request was prioritized or flagged), plus matching checks in `Assemble & Check` and `Grade`, then a rerun of all 32 emails.

## 4. LINE error alert

- `Error Alert → LINE` starts from n8n's Error Trigger. It sends the workflow name, the failed node, the error message and the execution link to my LINE through a LINE Official Account, using the Messaging API push endpoint. `Inquiry Assistant v2` and `Gmail Health Check` both use it as their error workflow.
- Found by Claude in the n8n source: when the Gmail credential expires, the Gmail Trigger only writes a log line. No failed execution is created, so the error workflow never runs. `Gmail Health Check` reads one Gmail label once a day; with an expired credential that node fails and the alert goes out. A manual run on 2026-10-21 read the label.
- Test: a temporary workflow that failed on purpose every minute. LINE answered 401 several times before the alert went through: first with the placeholder token, twice with "Authorization header required" because the `Bearer ` prefix was missing (the second time most likely a full-width space after `Bearer`), and once with "Authentication failed" because a wrong token was pasted. The credential was then changed to n8n's Bearer Auth type, which adds the prefix itself. At 2026-10-21 17:49 LINE accepted the message and returned a message ID (`sentMessages`).
- Changing the error workflow in the settings of a published workflow took effect without publishing again: the setting was changed at 17:26:45 and the error at 17:27:05 already used it.

Gaps:

- `Read & Classify` and `Draft Reply` continue on error, so an empty Anthropic balance or a revoked key sends every email to `human_review` without an alert.
- No throttling. The free LINE plan allows 200 push messages a month, and an error that repeats every minute would use them up.
- If the computer is off, the alert is off too.

## 5. Schedule delays on the self-hosted instance

| Schedule | Expected | Actually ran | Late by |
|---|---|---|---|
| Daily summary | 10/21 18:00 | 10/21 18:00:31 | 0:00:31 |
| Daily summary | 10/22 18:00 | 10/23 00:02:58 | 6:02:58 |
| Gmail Health Check | 10/22 09:00 | 10/22 15:02:39 | 6:02:39 |
| Gmail Health Check | 10/23 09:00 | 10/23 18:45:15 | 9:45:15 |

Times are Taipei time. The instance time zone is Asia/Taipei, and the 10/21 summary ran on time, so the time zone is not the cause. The computer was shut down on both nights, and the jobs ran late after it was turned back on.

The late 10/22 summary also summarized the wrong day. `Get Today's Log` uses the date at the moment it runs, so the run at 00:02 on 10/23 summarized 10/23 (0 emails), and the emails from 10/22 never got a summary. Plan: summarize the day the schedule was meant for, or every day since the last summary, instead of "today".
