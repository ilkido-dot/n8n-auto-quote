## 這一輪看出什麼

- LLM 抽資料的部分，10 封都照規則做：沒有自己編數量，沒有從引用的舊信抓出品項，否定句和中英混用都處理對了。
- 6 個失敗全部出在 LLM 後面那段固定的程式：它假設每個欄位都有值、每個品項都查得到。`null` 變成 `$0` 的報價，而不是停下來。
- T07 最危險：只報了一部分的 $720，看起來像完整的報價。

## 建測試時發現的問題（v1 之前）

1. Output Parser 裡還是 n8n 的預設範例格式（`state` / `cities`）→ 它什麼都沒在檢查。
2. 舊 prompt 的格式範例寫 `"數量": 0` → 客人問「X 有沒有貨」時，LLM 填了 `0`。
3. 舊的 Code 節點用 `$input.first()` → 一次 10 封信時，另外 9 封會被略過，也沒有錯誤訊息。

## v2 的修正計畫（步驟 3）

- 以下情況轉人工：`是新詢價` 是 false、任何一個 `數量` 是 null、任何品項在價目表查不到、合計超過 100 棵。
- 尺寸是 null、而且這個品種在價目表只有一種尺寸時，由程式補上（不交給 LLM）。

## 這次結果的限制（要寫進 README）

- 10 封信是我寫的，每封各跑一次。10/10 只說明規則在這些情況有效，不代表系統可以上線。
- LLM 每次的輸出可能不同，要多跑幾輪才能相信這個通過率。
- T06 是靠可接受的替代結果通過的：拼錯的品名轉人工，不自動更正（刻意這樣設計：猜錯會報成別的植物）。
